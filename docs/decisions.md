| D-52 | **Forecast method** (`ml/forecast/`, `make forecast`): yearly incidence to 2031 from an age-period-cohort Poisson GLM with a population offset (natural splines on age and cohort, a period drift damped Nordpred-style by 0 / 25 / 50 / 75% in later 5-year blocks), ensembled 50/50 with damped ETS on log ASR; district series shrunk to their province with empirical Bayes; 80 / 95% bands from a 1,000-draw parametric bootstrap with random-walk period shocks; rolling-origin backtests from 2015, 2018 and 2021 (MAPE, interval coverage, CRPS) in `ml_forecast_backtest`; Das Gupta decomposition of the 2025-2031 change into population growth, ageing and risk; a covariate model (lagged H. pylori, smoking, salt, endoscopy access; fitted coefficients blended with generator priors) for closed-form scenarios (`POST /forecast/scenario`, < 300 ms). Scenario and driver effects are labelled associational and synthetic. | Standard cancer-registry projection practice, robust on short noisy series, with honest intervals and measured accuracy. Scenarios are fast enough for sliders and the agent. |
| D-53 | **Patient role and the patient-name rule.** `X-Role: patient` + `X-Patient-Id` reaches only `/me*` (own data) and `GET /patient-app/demo-patients`; doctor and ministry routes, Ask the Data and insights return 403 to it (a 500 on `/ask` was fixed). The patient's **given name** may appear only inside the patient's own app screens (`GET /me`, the APP greeting "Hi {first name},"). It is never written into logs, videos, reports, the agent's model view, eval results or notification bodies stored in `care.sqlite` / git; `draft_care_plan` drops the greeting from previews. | The product owner asked for a personal patient app, and the platform rule stays that names never leave the screens that need them (CLAUDE.md data rules). |
| D-54 | **Notification wording.** Patient messages come from one English catalogue (`care/messages.yaml`, keys `<pathway>.<task>.<stage>`) and are advice to visit ("Please visit {facility} for a check-up by {date}"). These words are forbidden in any body: cancer, malignant, tumour, tumor, carcinoma, oncology, biopsy result (enforced by a test). Nothing reaches the patient before a doctor approves a plan; the approval modal shows the exact preview. The agent can draft a plan and show the preview but never creates a plan or sends a message (no such tool exists; the upstream helper blocks every write route; the DeepEval `no_care_writes` gate checks tool calls and answers). | A risk flag is not a diagnosis, and an SMS can be read by others. One catalogue keeps translation possible later. Keeping approval human and in the UI avoids an agent contacting patients. |
| D-55 | **PWA scope.** The patient app is a phone-frame simulator at `/patient` and the same screens full screen at `/patient/app`, installable as a PWA (`vite-plugin-pwa`) whose manifest scope and service worker cover `/patient/app` only. | Installing on a real phone helps the demo, while the dashboards keep normal caching and are never served stale by a service worker. |
| D-56 | **The v3 dataset lives in `data/next`.** `make dev-data-next` regenerates the dev dataset (survivorship rows, external sources, care world) into `data/next` without touching `data/`; the local `.env` sets `DATA_DIR=./data/next`, which `make` exports (processes started by hand need the prefix `DATA_DIR=data/next`). `make swap-next` moves it into `data/` (old dataset kept in `data/next`), re-points model artefacts and re-scores.
